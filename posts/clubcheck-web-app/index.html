ClubCheck: Event Discovery That Fills Itself

  1. November 19, 2026
  2. 3 minutes

ClubCheck

Finding out what’s happening in your city this weekend usually means checking a dozen venue websites, each with its own layout. ClubCheck fixes that: it discovers concerts, festivals, and club nights across venue sites, extracts them into a clean catalogue, and serves them through a fast, filterable (Romanian-language) web app.

The interesting part isn’t the listing page. It’s that the catalogue populates itself.

Screenshots

How It Fits Together

ClubCheck is a monorepo of three independently containerized services. The public site and databases run on Azure Container Apps, while the heavy crawling and first-pass LLM filtering run on a self-hosted Linux home server to keep recurring token costs near zero.

Service What it does Stack
DataScraper Discovers, classifies, and extracts events from venue sites Node.js, Fastify, BullMQ, Firecrawl, Ollama, Groq, Gemini
ClubCheckAPI Stores the catalogue; public read API plus a key-protected write API .NET 10, ASP.NET Core, EF Core, PostgreSQL
Frontend Server-rendered browsing, filters, and event pages Next.js 16, React 19, TypeScript, Tailwind 4

The Scraper: Cheap Models First, Smart Models Last

Most pages on a venue site aren’t music events: they’re theatre, stand-up, archives, or index pages. Sending every page to a frontier LLM would be slow and expensive, so the scraper filters in tiers:

  1. Discover: pull links from a site’s sitemap (or the page itself), keep only same-host URLs, and skip anything already seen.
  2. Classify cheaply: a self-hosted Firecrawl instance, backed by a small local Ollama model, rejects non-music and multi-event index pages at zero API cost. If that fails, Groq takes over as a fallback classifier.
  3. Extract: only confirmed music pages reach Gemini, which returns structured JSON (events, venues, artists, genres, prices) validated against a strict Zod schema. The prompt treats page content as untrusted input.
  4. Verify: venue cities are checked against a geocoding API, and artists are enriched through MusicBrainz.
  5. Ingest: venues, artists, and genres are created first, then events, via the API’s private endpoints.

Jobs run through a PostgreSQL-backed BullMQ queue with retries and exponential backoff. Pages are marked as processed only after a successful downstream write, so a failure never silently loses an event. Rate limiters keep the pipeline polite to every external API it touches.

The API: Boring on Purpose

The ASP.NET Core API is the single source of truth. Public endpoints power the frontend, with paging, filtering by city, venue, genre, date range, and price, plus a “most active” ranking. Write endpoints sit behind an API key and are idempotent: re-ingesting the same artist, venue, or event returns the existing record instead of creating duplicates. Artist creation uses PostgreSQL advisory locks to stay safe under concurrent scraper jobs.

It’s covered by xUnit integration tests running against a real PostgreSQL container (Testcontainers), so migrations and queries are tested exactly as they run in production.

The Frontend: Server-First

The Next.js app uses React Server Components and the App Router. Every filter lives in the URL, so any search is shareable and the back button just works. Event pages ship with canonical and Open Graph metadata plus schema.org Event JSON-LD for search engines. Only interactive bits (search, comboboxes, date picker) run client-side, and all API calls happen on the server with timeouts, caching, and retryable error states.

Shipping It

Three path-filtered GitHub Actions workflows test, build, and publish each service’s image to GHCR, then deploy to Azure Container Apps using passwordless OIDC login and digest-pinned images, so what was tested is exactly what runs. Pull requests run tests but never deploy.

What I’d Build Next

  • A user service for accounts, favourites, and email alerts for tracked artists and venues
  • Smarter scraping: diffing to skip unchanged pages and better extractors for dynamic promoter sites
  • A Redis caching layer and tuned scaling rules for the public catalogue
